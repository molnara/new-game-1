# Implementation Plan: Developer Foundations

**Branch**: `001-dev-foundations` | **Date**: 2026-09-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-dev-foundations/spec.md`

## Summary

Deliver the four developer-facing systems the constitution already assumes exist — structured
session logging, an in-game dev console, a screenshot harness that works without a display, and a
one-command verification gate — plus a fifth added after the spec was first written: a performance
overlay with frame-time statistics written to the session log.

The technical approach keeps every decision-bearing piece engine-free. `CommandRegistry`, the
command-line parser, and the frame-time histogram that produces the percentile statistics are plain
C# in `src/Core`, unit-tested with xUnit. Logging is consumed
through `Microsoft.Extensions.Logging.Abstractions` in Core and configured with Serilog (file sink
plus a Godot sink) in `src/Game/Infrastructure`. The console and screenshot harness are code-built
autoloads in `src/Game/Autoloads` — the console a `CanvasLayer`, the harness activated by a user
command-line argument. Verification is a shell script chaining build, a code-style
check, Core tests, and a captured screenshot compared against a golden image with ImageMagick.

Four planning spikes corrected assumptions rather than confirming them. Capture does **not** work
under `--headless`, only under `xvfb-run` with a real rendering driver (R1). The renderer must be
`forward_plus` through software Vulkan, matching the host editor, not the reduced `gl_compatibility`
one (R10). And the engine's own FPS counter reads a frozen `1.0` in short runs, so frame time must
be accumulated from the per-frame delta instead (R11). The fourth, run after constitution v1.1.0
added principle VI, found that `dotnet format` against the repository's four-line `.editorconfig`
catches whitespace and nothing else — so populating that file is a task of this feature, not a later
tidy-up (R13). See [research.md](./research.md) for the evidence behind each.

## Technical Context

**Language/Version**: C# / .NET 10 (`net10.0`), Godot 4.7.2 (.NET / Mono build)

**Primary Dependencies**: `Microsoft.Extensions.Logging.Abstractions` 10.0.11 (Core-facing
abstraction), Serilog 4.4.0 + `Serilog.Extensions.Logging` 10.0.0 + `Serilog.Sinks.File` 7.0.0
(Game-side implementation), xUnit 2.9.3 + Shouldly 4.3.0 (tests). All are already referenced in
`NewGame1.csproj` / `NewGame1.Core.csproj`; this feature adds no new NuGet package, the profiling
work included — its inputs are Godot's built-in `Performance` monitors and `/proc/self/status`
(research R11).

**System tooling**: ImageMagick 6.9.12 (`compare`, `convert`, `identify` — note: the IM7 `magick`
wrapper is **not** installed), `xvfb-run`, Mesa llvmpipe (OpenGL 4.5 software) and Mesa lavapipe
(Vulkan 1.4 software, used for Forward+ captures — see research R10).

**Code style**: defined by `.editorconfig` and the .NET analyzers configured in
`Directory.Build.props` (`EnableNETAnalyzers`, `AnalysisLevel=latest-recommended`), enforced by
`dotnet format --verify-no-changes` as a `verify.sh` stage (constitution VI). The `.editorconfig`
currently in the repository is four lines and defines only a character set; this feature expands it
into an actual C# style configuration, because a format gate against the current file passes
unconditionally (research R13).

**Version control**: `*.cs.uid` files generated by Godot are committed alongside their scripts;
`.gitignore` is left unchanged (research R15). Without them a rename mints a new UID and any scene
referencing the script by `uid://` loses it.

**Storage**: Plain-text rolling log files under the Godot user data directory
(`~/.local/share/godot/app_userdata/new game 1/logs/`, confirmed by spike). PNG artifacts under
`artifacts/` (gitignored). Golden reference PNGs under `tests/golden/` (committed).

**Testing**: two tiers, both shipping in this feature (constitution II; clarified 2026-09-02,
reversing the 2026-09-01 deferral). Fast tier: xUnit against `src/Core` via `dotnet test`, in
milliseconds, no engine. Slow tier: GoDotTest in `tests/Game.Tests`, run by launching the game under
`xvfb-run` with `--run-tests --quit-on-finish`. The slow tier compiles into the game assembly rather
than a separate one — GoDotTest reflects over the executing assembly — which is why
`NewGame1.csproj` already excludes it under `ExportRelease` (research R14). The slow tier stays the
exception: it covers node, input, and frame-timing behavior with no Core representation, and nothing
that could have been a Core test belongs in it.

**Target Platform**: Linux dev container (no GPU, no display, software rendering only); Arch Linux
host runs the same engine and SDK versions and drives the Godot editor against this same folder with
hardware rendering.

**Project Type**: Single Godot game project with an engine-free core library.

**Performance Goals**: 60 fps unaffected by logging — routine log entries must not cause a
per-frame disk write (SC-007: console opens within one frame).

**Constraints**: Core must not reference Godot (constitution I). Warnings and errors must reach
disk immediately; debug/info may batch (clarified, FR-005). Capture must wait a fixed frame count,
never a wall-clock delay (clarified, FR-026). Verification must run unattended with no display
(FR-032).

**Measurement validity — performance numbers from this container are not real** (applies to the
profiling story, FR-037 onward): the container renders through Mesa's software rasterizers —
llvmpipe for OpenGL, lavapipe for Vulkan — with no GPU. A frame time measured here describes a
software rasterizer running on the build machine. It is not a measurement of the game, and it is not
a valid performance signal. Three consequences bind implementation:

1. **No automated test may assert an absolute frame-time, frames-per-second, or draw-call budget
   from a container run.** Such a test would pass or fail on how busy the build machine is, and its
   green result would mean nothing about the game. This is the specific mistake this constraint
   exists to prevent.
2. **Relative comparisons within one environment remain valid**, which is how the overlay's own cost
   must be checked. FR-040 and SC-013 bound the overlay's cost to under 1 millisecond — that is a
   difference between overlay-on and overlay-off measured in the same place, and it is testable
   here. An absolute frame-time budget is not.
3. **Any absolute performance figure offered as evidence must come from a run on real hardware**,
   which means the host. Statistics captured in the container are still worth logging — they prove
   the sampling, percentile, and record-writing machinery works — but they must never be quoted as
   what the game performs like.

The GPU is deliberately not exposed to this container: verification stays on software rendering so
goldens remain reproducible and immune to host driver updates (research R2 and R10). Exposing it
later is a separate decision that changes none of the above, because verification would stay on the
software path regardless.

**Scale/Scope**: Single developer, single-player game. ~16 new source files, ~3 slow-tier test
files, ~3 shell scripts, one placeholder scene, plus two existing root files edited
(`.editorconfig`, `README.md`). No csproj change: `NewGame1.csproj` already carries the GoDotTest
reference and the `ExportRelease` exclusion the slow tier needs. Log retention 10 sessions; console history bounded.

### Constitution v1.1.0 delta — principle VI (Standards Are Automated)

Principle VI was added to the constitution after this plan was first written. It is the only
amendment in v1.1.0, and it changes this plan in five places. None of it alters the architecture: it
adds one verification stage and three obligations that were previously unowned, plus one note
recorded so its absence elsewhere is not read as an oversight.

**1. `verify.sh` gains a code-style stage.** The amended "Development Workflow & Quality Gates"
section names the gate as build → `dotnet format` → Core tests → Godot tests → screenshot. The plan's
script was build → Core tests → screenshot → golden compare. The format stage is inserted second,
directly after build, matching the constitution's order and reusing the restore the build just did.
[contracts/cli-scripts.md](./contracts/cli-scripts.md) carries the updated stage table, and `spec.md`
FR-028 has been amended to list the stage (see the scope note below).

The constitution's ordering also names a Godot test stage, and that stage now exists too — see the
separate section below. The gate list is satisfied literally rather than by argument.

**2. `.editorconfig` must be expanded, as work inside this feature.** VI makes `.editorconfig` and
the analyzers the definition of code style. The repository's file is four lines and defines a
character set. The spike in research R13 confirmed the consequence: with that file, `dotnet format`
reports whitespace defects and passes an unused `using`, `String` for `string`, and misordered
directives with exit 0. Adding the stage without expanding the file would produce a gate that is
green because it checks nothing — the failure mode most likely to be mistaken for coverage. Expanding
it is therefore a task of this feature, sequenced before the `verify.sh` stage that depends on it.

Because VI also forbids settling style by review comment, the content of that file is the decision
record: any rule this project cares about has to appear there with an explicit severity at `warning`
or above, or `dotnet format` will not enforce it.

**3. Godot naming binds the placeholder scene and the autoloads.** VI fixes three rules: scene files
are PascalCase and match the class name of their root script, signals are PascalCase, and exported
fields carry no prefix. `scenes/Main.tscn` (FR-033) consequently needs a root script whose class is
`Main`, which the structure below now names as `src/Game/Main.cs`. It had been left implicit. The
console and performance overlay are code-built `CanvasLayer`s, so their contribution is limited to
PascalCase signal names and unprefixed `[Export]` fields where they use either.

**4. Documentation rules constrain what this feature is allowed to write.** VI states that `specs/`
is the design record, the root `README` covers running the project, per-folder `README`s and separate
ADR documents must not be created, and XML doc comments appear only on public `src/Core` APIs. Two
consequences: no `README` may be added under `scripts/`, `tests/golden/`, or `artifacts/` to explain
them — the contracts in this directory are where that belongs — and the XML doc comment budget falls
on the public surface of `CommandRegistry`, `FrameTimeHistogram`, `IScreenshotService` and
`IPerformanceCounters`, with the Game-side adapters getting none.

The root `README` today documents only the container workflow. VI says it covers running the project,
and this feature is the one that first makes the project runnable and verifiable, so extending it
with how to run the game, capture a screenshot, and run `verify.sh` is in scope here.

**5. `dotnet format` adds no Complexity Tracking entry.** It ships in the .NET SDK already installed;
it is not a new framework, addon, or third-party dependency, so principle V requires no justification
for it. Recorded explicitly so its absence from that table reads as a decision rather than an
oversight.

### Engine test tier — deferral reversed (2026-09-02)

On 2026-09-01 a clarification answered "fast engine-free tests only for now", and `tests/Game.Tests`
was left uncreated. On 2026-09-02 the developer reversed that: both tiers ship from the start, and
`verify.sh` runs both. `spec.md` carries the superseding clarification, FR-028c/d/e, and SC-015/016;
research R14 carries the mechanics.

**Why the original deferral does not hold up.** It rested on "nothing in this feature needs an engine
test". The evidence against that was already in this directory: `quickstart.md` Story 2 opens with
*"Needs an interactive display, so this one is run on the host rather than in the container"* and
then lists eight steps performed by hand — including FR-011 (opening the console must not deliver the
backtick into its own input field) and SC-007 (the console opens within one displayed frame). Those
are node and input behavior with no Core representation, which is the exact condition constitution II
names for the slow tier. The tier was not unnecessary; its work had been converted into a manual
checklist, which is the failure mode principle II exists to prevent.

**What goes in it, and what does not.** The slow tier stays the exception (constitution II). It takes
only what cannot be expressed engine-free:

| Covered by the slow tier | Why it cannot be a Core test |
|---|---|
| Console opens and closes on the toggle key (FR-010) | Requires the engine's input pipeline and node tree. |
| The toggle keystroke does not land in the console's input (FR-011) | Same, and it is the specific defect most likely to regress silently. |
| Console opens within one displayed frame (SC-007) | Needs real frame delivery. |
| Overlay toggles on and off, and sampling runs regardless (FR-038, FR-045) | Node lifecycle across frames. |
| Harness waits a fixed frame count before capturing (FR-026) | Frame counting is the behavior under test. |

Everything else stays in Core: the registry, parser, help formatting, bounded history, retention
policy, histogram and percentiles. Before adding any slow-tier test, constitution II's question
applies first — could this move into Core instead.

**Where it lives.** `tests/Game.Tests`, compiled into the game assembly rather than a separate one,
because GoDotTest reflects over the executing assembly (research R14). `NewGame1.csproj` already
carries both halves of that arrangement — the `Chickensoft.GoDotTest` package reference and the
`ExportRelease` compile exclusion that keeps tests out of shipped builds. No csproj change is needed
to stand the tier up, which is a fair sign the skeleton always expected it.

**The entry point is `src/Game/Main.cs`.** Constitution VI put that file in the plan an hour earlier,
to give `scenes/Main.tscn` a root script matching its name. R14 gives it a second job: GoDotTest is
started from the main scene's `_Ready()`, guarded by `#if DEBUG`, which checks the command line and
hands the assembly to the runner instead of starting the game. GoDotTest's own documented example
names that class `Main`, so the two requirements coincide. The consequence worth flagging: `Main.cs`
now branches three ways — run tests, capture a screenshot, or be the placeholder scene — and every
automated path in this feature runs through it, so it is the one file here where a mistake breaks
verification itself rather than a feature.

**Running it is a Godot run, not a `dotnet` one**, so R1 and R10 apply: `xvfb-run` rather than
`--headless`, Forward+ through software Vulkan, `--audio-driver Dummy`. R4 does *not* — GoDotTest
sets its exit code deliberately (0 pass, 1 fail), which the spike measured.

**Spike-verified (2026-09-02).** The tier was stood up end to end in this container and then removed:
GoDotTest launches under `xvfb-run`, discovers suites, runs them, lets a test manipulate the live
scene tree, reports per-test results with file and line on failure, and quits on its own. No csproj
change was needed — the skeleton's existing package reference and `ExportRelease` exclusion were
sufficient. Research R14 carries the measurements.

**The one trap the spike found**: a run that executes *no* tests — a mistyped suite filter, or a
configuration that excluded `tests/Game.Tests/**` — exits **0** and prints
`Passed: 0 | Failed: 0 | Skipped: 0`. So the stage must assert a non-zero passed count as well as
branching on the exit code. This is structurally the same defect as a format gate against an empty
`.editorconfig` (R13): the second time in this feature that a gate could have shipped green while
verifying nothing.

### Scope deviation requiring the developer's attention

The feature description for this plan asks for **golden screenshot comparison with ImageMagick**.
The spec's Out of Scope section explicitly excludes it ("Automatic comparison of screenshots against
golden reference images, and any diffing or approval workflow around them").

Constitution IV independently *requires* golden reference images, so the plan follows the
constitution and the newer instruction and brings golden comparison in. `spec.md` has been amended
in the same commit to match — the Out of Scope bullet is replaced and FR-035/FR-036 added — so the
two documents do not contradict each other going into `/speckit-tasks`. This is flagged rather than
silently absorbed because it grew the feature.

**Second amendment, from constitution v1.1.0.** Principle VI likewise required editing `spec.md`
rather than only this plan: FR-028 now lists the code-style stage, FR-028b states the requirement
that style be machine-checked against a checked-in configuration, SC-014 makes it measurable, and the
"Verification stages" assumption names the new stage and why it exists. The same reasoning applies —
the constitution outranks the spec (Governance), so the conflicting document is corrected rather than
worked around. This one grew the feature by one script stage and one configuration file.

## Complexity Tracking

> Constitution V requires written justification for any third-party library or framework.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| **Serilog** (+ `Serilog.Extensions.Logging`, `Serilog.Sinks.File`) as a third-party logging library | FR-005 needs per-level flush control (warnings/errors immediately, debug/info batched), FR-006 needs bounded session-file retention, and FR-001 needs one timestamped file per run. Serilog provides all three as configuration, and it is already referenced in the repo skeleton. | Hand-rolling a `StreamWriter` logger was considered and rejected: getting rolling-file retention, per-level flush policy, and safe concurrent writes correct is materially more code than configuring an existing sink, and it is code with no consumer outside this project. `GD.print` alone was rejected because it cannot satisfy FR-002 (structured fields) or FR-005 (flush policy), and constitution III forbids it outside Infrastructure. |
| **`Microsoft.Extensions.Logging.Abstractions`** referenced by Core | Constitution I forbids Godot in Core, but Core code must still log. An abstraction package with no engine ties is the mechanism that makes that possible. | A hand-written `ILog` interface was rejected: it would be a near-identical reimplementation of a standard interface, and would force an adapter layer between Core's logger and Serilog that the standard abstraction already provides for free. |
| **ImageMagick** as a system dependency for golden comparison | Constitution IV requires golden reference screenshots; comparing PNGs pixel-wise needs an image differ. ImageMagick is already installed in the container. | Writing a C# pixel comparator was rejected as unnecessary: the comparison happens in shell scripts outside the game process, where invoking an installed tool is one line. It adds no NuGet dependency and no code to maintain. |

Note: ImageMagick 6 is installed, which provides `compare`/`convert`/`identify` as separate binaries
and **not** the IM7 `magick` wrapper. Scripts must call `compare` directly.

Note: `dotnet format`, added as a gate by constitution VI, ships in the .NET SDK and needs no entry
above — it is not a new dependency. The `.editorconfig` expansion it requires is likewise
configuration, not a library.
